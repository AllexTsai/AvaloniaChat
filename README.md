# AvaloniaChat

## Overview

A small chat UI built with Avalonia 12 to get familiar with the differences between Avalonia and WPF. It streams answers from a local Ollama `phi3` model.

This is a practice project: it has no conversation history, no token budget, and no output checks, and it is not production code.

## Requirements and Run

Requirements:

- .NET 10 SDK (the project's `TargetFramework` is `net10.0`)
- Ollama, with the `phi3:latest` model pulled
- The app connects to `http://localhost:11434/`, sends the model name `phi3`, and sets `num_ctx` to 2048

From the repository root:

```
dotnet build AvaloniaChat/AvaloniaChat.csproj
dotnet run --project AvaloniaChat
```

Without Ollama, using fake replies:

```
dotnet run --project AvaloniaChat -- --fake
```

Command-line options:

| Option | Description |
|---|---|
| `--fake` | Use the fake service (the default is Ollama). |
| `--max-tokens N` | Ollama `num_predict`. Range 16 to 2048, default 512. |

Other unknown arguments are ignored. If `--max-tokens` has no value, is not an integer, or is out of range, the program prints an error and exits with code 2.

## Differences from WPF I noticed

1. The `.axaml` extension lets editors and tools tell that the file is Avalonia XAML. (I did not find an official explanation of the exact reason, so I do not claim it is about the compiler.)
2. The theme must be declared: `App.axaml` needs `FluentTheme` under `Application.Styles`, while WPF has built-in default styles.
3. `ViewLocator` is an optional class that ships with the template (it implements `IDataTemplate`). You can also write `DataTemplate`s in XAML, as in WPF. The template notes say the default `ViewLocator` is not trimming-friendly.
4. The entry point is in `Program.cs` (`Main` and `BuildAvaloniaApp`); in WPF it is generated from `App.xaml`.
5. Compiled bindings are on by default (Avalonia 12.1.5). The type comes from `x:DataType` or is inferred from `ItemsSource`; if it cannot be inferred, it is a compile error. For dynamic cases use `{ReflectionBinding}`. Run-time binding errors appear only in the debug output, not in the `dotnet run` terminal.
6. `TextBox.Text` writes back on every text change by default in Avalonia; in WPF it writes back when the box loses focus.
7. The UI thread is reached through `Dispatcher.UIThread`. In WPF a `Dispatcher` belongs to the thread that created the object, and an ordinary program has a single UI thread.
8. Styles use selectors and can be switched by data with `Classes.xxx="{Binding ...}"`. Priority: a value set directly on the control wins; conditional selectors beat type selectors; at the same level the later declaration wins; there is no CSS-style specificity.

## Observations

Each item below is a single run on one machine, and the clients differ (this app vs. `ollama run`), so they should not be compared directly.

- Test environment: Windows, Ollama 0.40.16, NVIDIA driver 581.83, GTX 1050 (4 GB).
- `phi3:latest` with `num_ctx` 2048 (this app): about 3.1 GB loaded, 77% on the GPU, about 18 tokens/s.
- `phi3:latest` with `num_ctx` 4096 (`ollama run`): about 3.9 GB loaded, 60% on the GPU, about 14.7 tokens/s.
- After updating Ollama, one reply ran for more than a minute without finishing (there was no output cap at that time, and the token count was not recorded). Later retests mostly finished in about 10 seconds. One run in this app (cap 512) hit the cap (done reason `length`, 512 tokens, about 30 seconds). I suspect a long output, but the cause is not confirmed.

## Limitations

- All numbers are single runs.
- Tested only on Windows.
- Tested only with phi3.
- No unit tests.
- Whether the server stops generating immediately after the client cancels was not measured.
